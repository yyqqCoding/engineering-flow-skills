# Engineering Flow Skills - 快速参考卡

## 6大核心技能速查表

### 🚀 develop - 统一开发流程
**何时使用**: 明确的功能开发需求  
**流程**: 需求澄清 → 计划编写 → TDD实施 → 完成交付  
**命令**: `/develop` 或自动触发  
**典型场景**: "添加用户登录功能"、"实现支付模块"

---

### 🔍 diagnose - 系统化问题诊断
**何时使用**: 任何 bug、测试失败、异常行为  
**流程**: 根因调查 → 模式分析 → 假设验证 → 修复实施  
**命令**: `/diagnose` 或自动触发  
**典型场景**: "登录返回500错误"、"测试间歇性失败"

---

### 🎨 design - 架构设计与方案规划
**何时使用**: 技术选型、架构讨论、不确定如何实现  
**流程**: 问题探索 → 方案生成 → 决策支持 → 文档输出  
**命令**: `/design`  
**典型场景**: "不确定用什么数据库"、"需要讨论架构方案"

---

### ✅ review - 多维度代码审查
**何时使用**: 任务完成后、功能实现后、合并前  
**审查维度**: 需求符合性、正确性、可读性、可测试性、设计质量、安全性  
**命令**: `/review` 或由其他技能调用  
**典型场景**: "审查这个PR"、"检查代码质量"

---

### 🛡️ boundary-test - 边界与极端情况测试
**何时使用**: 功能实现后、安全敏感功能、数据处理逻辑  
**测试类型**: 输入边界、状态边界、资源边界、数据边界、业务边界  
**命令**: `/boundary-test` 或由 review 调用  
**典型场景**: "测试极端情况"、"安全边界检查"

---

### ✨ refine - 代码质量精炼
**何时使用**: 测试通过后、发现代码重复、准备合并前  
**优化维度**: 简化、去重、可读性、性能、YAGNI检查  
**命令**: `/refine`  
**典型场景**: "重构这段代码"、"清理重复逻辑"

---

## 技能协作流程图

```
用户需求
    │
    ├─ 明确做什么 ────→ [develop]
    │                     ├─ 阶段1: 需求澄清
    │                     ├─ 阶段2: 计划编写
    │                     ├─ 阶段3: TDD实施 ─→ [refine] ─→ [review]
    │                     └─ 阶段4: 完成交付
    │
    ├─ 不确定如何做 ───→ [design] ─→ 方案确定后 ─→ [develop]
    │
    ├─ 有bug需要修复 ──→ [diagnose]
    │                     ├─ 根因调查
    │                     ├─ 模式分析
    │                     ├─ 假设验证
    │                     └─ 修复实施(TDD) ─→ [review]
    │
    └─ 代码质量改进 ───→ [refine] ─→ [review]
```

## 决策树：我该用哪个技能？

```
开始
  │
  ├─ 有问题要修？
  │   └─ YES → [diagnose]
  │
  ├─ 不确定技术方案？
  │   └─ YES → [design]
  │
  ├─ 明确要开发功能？
  │   └─ YES → [develop]
  │
  ├─ 代码已完成，需审查？
  │   └─ YES → [review]
  │
  ├─ 需要测试边界情况？
  │   └─ YES → [boundary-test]
  │
  └─ 代码能工作，想改进质量？
      └─ YES → [refine]
```

## 关键原则速记

### develop
- ✅ TDD 强制（RED-GREEN-REFACTOR）
- ✅ 需求必须澄清后再实施
- ❌ 不跳过计划直接写代码

### diagnose
- ✅ 根因优先，禁止症状修复
- ✅ 3次失败 → 质疑架构
- ❌ 不猜测，必须有证据

### design
- ✅ 至少2-3个方案对比
- ✅ 说明权衡和推荐理由
- ❌ 不产出代码（仅方案）

### review
- ✅ 6维度全面检查
- ✅ Critical问题阻塞进展
- ❌ 不超过5轮修复循环

### boundary-test
- ✅ 覆盖5类边界
- ✅ TDD之后补充
- ❌ 不仅测试happy path

### refine
- ✅ 绿色测试后才重构
- ✅ YAGNI严格检查
- ❌ 不改变外部行为

## 常见场景映射

| 用户说... | 使用技能 | 理由 |
|----------|---------|------|
| "我想做个XX功能" | develop | 明确的开发需求 |
| "有个bug：..." | diagnose | 问题诊断和修复 |
| "不知道用XX还是YY" | design | 技术选型讨论 |
| "帮我review这个代码" | review | 代码质量检查 |
| "测试一下边界情况" | boundary-test | 边界和极端测试 |
| "这代码太乱了，优化下" | refine | 质量改进 |
| "做XX，但不确定怎么做" | design → develop | 先探索后实施 |
