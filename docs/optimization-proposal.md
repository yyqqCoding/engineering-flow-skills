# Engineering Flow Skills 优化方案

## 执行摘要

基于对 superpowers、mattpocock/skills 和 ponytail 三个优秀技能库的深入分析，结合软件工程最佳实践，本方案提出了一套精简、高效的技能体系优化建议。

## 当前状态分析

### 现有 Superpowers 技能清单（14个）

1. **brainstorming** - 创意探索和设计确认
2. **writing-plans** - 实施计划编写
3. **executing-plans** - 计划执行（批处理模式）
4. **subagent-driven-development** - 子代理驱动开发
5. **test-driven-development** - 测试驱动开发
6. **systematic-debugging** - 系统化调试
7. **verification-before-completion** - 完成前验证
8. **requesting-code-review** - 请求代码审查
9. **receiving-code-review** - 接收代码审查反馈
10. **finishing-a-development-branch** - 完成开发分支
11. **using-git-worktrees** - Git工作树管理
12. **dispatching-parallel-agents** - 并行代理调度
13. **writing-skills** - 编写技能
14. **using-superpowers** - 使用说明（引导）

### 核心问题识别

1. **技能数量过多**（14个）- 增加认知负担
2. **职责重叠** - executing-plans 和 subagent-driven-development 本质相同
3. **粒度不一致** - 有些是完整流程，有些是细节规则
4. **缺失关键能力** - 代码审查流程不够系统化，缺少边界测试策略

---

## 优化方案：精简为 6 大核心技能

### 🎯 设计原则

1. **高内聚低耦合** - 每个技能职责单一清晰
2. **完整性** - 覆盖完整的软件开发生命周期
3. **可组合性** - 技能之间可以灵活组合使用
4. **实用主义** - 基于真实失败模式，非理论构建

---

## 新技能体系架构

### 1️⃣ **develop** - 统一开发流程技能

**合并来源**：brainstorming + writing-plans + subagent-driven-development + executing-plans

**核心理念**：从需求到实现的完整开发流程

**触发时机**：
- 用户提出新功能需求
- 用户要求实现某个特性
- 明确的开发任务

**流程阶段**：

```
阶段1: 需求澄清 (Requirement Clarification)
├─ 探索项目上下文
├─ 逐个提问澄清（一次一个问题）
├─ 提出2-3种方案 + 权衡分析
└─ 呈现设计方案并获得用户批准

阶段2: 计划编写 (Plan Writing)  
├─ 写入设计文档到 docs/specs/YYYY-MM-DD-<topic>-design.md
├─ 创建实施计划到 docs/plans/YYYY-MM-DD-<topic>-plan.md
├─ 任务分解（每个任务2-5分钟）
└─ 明确文件路径、代码、验证步骤

阶段3: 执行实施 (Implementation)
├─ 创建隔离工作树（using-git-worktrees）
├─ 逐任务执行（TDD red-green-refactor）
├─ 每任务后代码审查
└─ 持续集成测试

阶段4: 完成交付 (Completion)
├─ 全量测试验证
├─ 呈现选项（merge/PR/keep）
└─ 清理工作环境
```

**关键改进**：
- **消除 develop-confirm**：需求讨论是开发必经步骤，无需单独技能
- **统一执行模式**：subagent 或 inline 执行由工具能力决定，非独立技能
- **内置 TDD**：作为实施阶段的强制规则，非可选附加项

---

### 2️⃣ **diagnose** - 系统化问题诊断

**合并来源**：systematic-debugging + verification-before-completion

**核心理念**：根因分析优先，症状修复禁止

**触发时机**：
- 任何 bug、测试失败、异常行为
- 性能问题、构建失败
- 集成问题

**四阶段流程**：

```
阶段1: 根因调查 (Root Cause Investigation)
├─ 仔细阅读错误信息
├─ 稳定复现问题
├─ 检查最近变更
├─ 多组件系统：每层边界添加诊断日志
└─ 追踪数据流向

阶段2: 模式分析 (Pattern Analysis)
├─ 查找工作示例
├─ 对比参考实现
├─ 识别差异
└─ 理解依赖关系

阶段3: 假设验证 (Hypothesis Testing)
├─ 单一假设明确陈述
├─ 最小化变更测试
├─ 验证后再继续
└─ 不确定时明确说明

阶段4: 修复实施 (Fix Implementation)
├─ 创建失败测试用例（必须）
├─ 单一修复
├─ 验证修复（verification-before-completion 规则）
└─ 3次修复失败 → 质疑架构设计
```

**关键改进**：
- **内置验证规则**：修复前必须有证据，完成前必须验证
- **架构质疑机制**：3次失败自动触发架构反思
- **多层系统诊断**：明确的边界日志策略

---

### 3️⃣ **design** - 架构设计与方案规划

**新增技能** - 填补现有空白

**核心理念**：面向不确定性的架构探索

**触发时机**：
- 用户不确定如何实现
- 需要技术选型
- 架构重构讨论
- 多方案权衡
- 技术调研

**流程**：

```
阶段1: 问题空间探索
├─ 理解当前系统约束
├─ 识别关键决策点
├─ 明确成功标准
└─ 识别风险和未知项

阶段2: 方案生成
├─ 生成 2-4 个候选方案
├─ 每个方案的权衡分析
│   ├─ 技术复杂度
│   ├─ 维护成本
│   ├─ 性能影响
│   └─ 可扩展性
└─ 推荐方案 + 理由

阶段3: 决策支持
├─ 视觉化架构图（可选）
├─ 原型验证（必要时）
├─ 风险评估
└─ 实施路径建议

阶段4: 文档输出
└─ 设计文档（不含实施计划）
```

**vs. develop 的区别**：
- **design**: 不知道做什么 / 如何做 → 架构探索
- **develop**: 知道做什么 → 需求澄清 → 实施

**关键价值**：
- 分离"探索"和"执行"两种思维模式
- 支持纯粹的技术讨论
- 可以不产出代码（仅方案）

---

### 4️⃣ **review** - 多维度代码审查

**合并来源**：requesting-code-review + receiving-code-review + 新增能力

**核心理念**：AI 写代码后的质量保障机制

**触发时机**：
- 任务完成后
- 功能实现后
- 合并前
- 重构后

**审查维度**：

```
1. 需求符合性 (Requirement Fidelity)
   ├─ 是否完成所有接受标准
   ├─ 是否有额外的未要求功能（YAGNI 检查）
   └─ 边界条件是否处理

2. 正确性 (Correctness)
   ├─ 逻辑错误
   ├─ 边界情况处理
   ├─ 错误处理完整性
   └─ 并发安全（如适用）

3. 可读性 (Readability)
   ├─ 命名清晰性
   ├─ 局部推理能力
   ├─ 复杂度控制
   └─ 注释必要性

4. 可测试性 (Testability)
   ├─ 测试覆盖充分性
   ├─ 测试有效性（能否发现缺陷）
   ├─ 测试维护性
   └─ 边界测试（新增重点）

5. 设计质量 (Design Quality)
   ├─ 职责单一性
   ├─ 耦合度
   ├─ 抽象合理性
   └─ 过度工程检测

6. 安全性 (Security)
   ├─ 输入验证
   ├─ 权限检查
   ├─ 敏感信息处理
   └─ 注入攻击防护
```

**审查流程**：

```
1. 生成审查包
   git diff BASE..HEAD > review-package.diff

2. 派发审查子代理
   - 输入：diff + 需求文档
   - 模型选择：根据复杂度
   - 输出：分级问题列表（Critical/Important/Minor）

3. 问题处理循环（最多5轮）
   Round 1-3: 恢复原实施子代理修复
   Round 4-5: 新子代理 + 更强模型
   每轮后：重新审查修复部分

4. 终止条件
   - 审查通过
   - 5轮后仍有问题 → 人工裁决
```

**关键创新**：
- **边界测试策略**：专门维度检查极端情况
- **分级问题处理**：Critical 阻塞，Minor 延迟
- **审查疲劳防护**：5轮上限 + 升级机制

---

### 5️⃣ **boundary-test** - 边界与极端情况测试

**新增技能** - 基于您的需求

**核心理念**：TDD 关注正常路径，boundary-test 关注破坏路径

**触发时机**：
- 功能实现后
- 审查发现边界遗漏时
- 安全敏感功能
- 数据处理逻辑

**测试策略矩阵**：

```
1. 输入边界 (Input Boundaries)
   ├─ 空值：null、undefined、""、[]、{}
   ├─ 极端值：MIN/MAX、0、-1、Infinity
   ├─ 格式错误：类型不匹配、格式异常
   └─ 特殊字符：SQL注入字符、XSS字符、Unicode边缘

2. 状态边界 (State Boundaries)
   ├─ 初始状态：未初始化时调用
   ├─ 转换边界：状态机边界条件
   ├─ 终止状态：清理后再次使用
   └─ 并发状态：竞态条件

3. 资源边界 (Resource Boundaries)
   ├─ 容量限制：内存耗尽、磁盘满
   ├─ 时间限制：超时、过期
   ├─ 连接限制：连接池耗尽
   └─ 权限边界：未授权访问

4. 数据边界 (Data Boundaries)
   ├─ 集合边界：空集合、单元素、巨大集合
   ├─ 数值边界：溢出、下溢、精度损失
   ├─ 字符串边界：空串、超长串、编码问题
   └─ 时间边界：时区、夏令时、闰秒

5. 业务边界 (Business Boundaries)
   ├─ 业务规则边界：金额为0、负数退款
   ├─ 权限边界：匿名、过期token
   ├─ 流程边界：跳过步骤、重复提交
   └─ 数据一致性：分布式事务失败
```

**实施方法**：

```
步骤1: 识别边界场景
- 分析函数签名和业务逻辑
- 列举所有边界类型
- 优先级排序

步骤2: 生成测试用例
test_empty_input()
test_null_input()  
test_max_value_overflow()
test_concurrent_access()
test_malicious_input()

步骤3: 预期行为定义
- 优雅降级 vs. 快速失败
- 错误信息清晰性
- 日志完整性

步骤4: 执行与验证
- 确认每个边界都被测试
- 确认失败模式符合预期
- 补充缺失的边界保护
```

**与 TDD 的关系**：
- **TDD**：功能正确性（happy path + 已知错误路径）
- **boundary-test**：鲁棒性（未预期的边界和攻击）
- **时序**：TDD 完成后 → boundary-test 补充

**关键价值**：
- 系统化覆盖"没想到的情况"
- 安全漏洞预防
- 生产环境鲁棒性

---

### 6️⃣ **refine** - 代码质量精炼

**合并来源**：部分 superpowers 理念 + mattpocock 简化哲学

**核心理念**：在工作代码上持续改进质量

**触发时机**：
- 功能完成且测试通过后
- 发现代码重复
- 复杂度过高
- 准备合并前

**优化维度**：

```
1. 简化 (Simplification)
   ├─ 移除不必要的抽象
   ├─ 内联仅用一次的函数
   ├─ 消除条件嵌套
   └─ 简化命名

2. 去重 (DRY - Don't Repeat Yourself)
   ├─ 识别语义重复（非形式重复）
   ├─ 提取共享逻辑
   ├─ 避免过度抽象
   └─ 保留有价值的重复（独立演化的逻辑）

3. 可读性 (Readability)
   ├─ 局部推理优化
   ├─ 命名精准化
   ├─ 注释最小化（代码自解释）
   └─ 控制流清晰化

4. 性能 (Performance)
   ├─ 热路径优化（有证据时）
   ├─ 算法复杂度改进
   ├─ 资源使用优化
   └─ 避免过早优化

5. YAGNI 检查 (You Aren't Gonna Need It)
   ├─ 移除未使用的代码
   ├─ 移除推测性功能
   ├─ 移除"为将来准备"的抽象
   └─ 保持最小可用实现
```

**红绿重构循环集成**：

```
RED: 写失败测试
  ↓
GREEN: 最小实现通过
  ↓
REFACTOR: 使用 refine 技能改进质量
  ↓
验证: 测试仍然通过
```

**安全约束**：
- ✅ 仅重构绿色测试的代码
- ✅ 每次重构后立即运行测试
- ✅ 一次只改一个维度
- ❌ 不改变外部行为
- ❌ 不添加新功能

**关键价值**：
- 明确的"质量改进"阶段
- 防止过度工程
- 保持代码简洁

## 完整开发流程示例

### 场景1：新功能开发（明确需求）

```
用户: "我想添加用户登录功能"

AI: 使用 develop 技能
  ├─ 阶段1: 需求澄清
  │   ├─ 问：认证方式？（密码/OAuth/SSO）
  │   ├─ 问：会话管理策略？
  │   ├─ 问：安全要求？（2FA、密码复杂度）
  │   └─ 呈现设计方案 → 用户批准
  │
  ├─ 阶段2: 计划编写
  │   ├─ 设计文档 → docs/specs/2026-07-25-login-design.md
  │   ├─ 实施计划 → docs/plans/2026-07-25-login-plan.md
  │   └─ 任务分解：Task 1-5，每个2-5分钟
  │
  ├─ 阶段3: 执行实施
  │   ├─ 创建工作树（using-git-worktrees）
  │   ├─ Task 1: 用户模型（TDD: RED→GREEN→REFACTOR）
  │   ├─ → review 技能检查 Task 1
  │   ├─ → boundary-test 检查边界（空密码、SQL注入）
  │   ├─ Task 2: 认证服务（TDD）
  │   ├─ → review + boundary-test
  │   └─ ...Task 3-5 重复
  │
  └─ 阶段4: 完成交付
      ├─ 全量测试通过
      ├─ 呈现选项：Merge / PR / Keep
      └─ 清理工作树
```

### 场景2：Bug修复

```
用户: "登录时输入空密码导致500错误"

AI: 使用 diagnose 技能
  ├─ 阶段1: 根因调查
  │   ├─ 阅读错误堆栈
  │   ├─ 复现：POST /login body={password: ""}
  │   ├─ 检查代码：auth.service.js:45 未验证空值
  │   └─ 根因：缺少输入验证
  │
  ├─ 阶段2: 模式分析
  │   ├─ 查找：其他endpoint有验证中间件
  │   ├─ 对比：/register 有 validateInput()
  │   └─ 差异：/login 缺少验证
  │
  ├─ 阶段3: 假设验证
  │   └─ 假设：添加 validateInput 可解决
  │
  └─ 阶段4: 修复实施
      ├─ 写失败测试（TDD）
      │   test("rejects empty password", async () => {
      │     const res = await post("/login", {password: ""});
      │     expect(res.status).toBe(400);
      │   })
      ├─ 运行测试 → 失败（验证 RED）
      ├─ 添加验证逻辑
      ├─ 运行测试 → 通过（验证 GREEN）
      └─ verification-before-completion：确认原始错误消失
```

### 场景3：技术方案讨论（不确定如何做）

```
用户: "我需要处理大量文件上传，但不确定用什么方案"

AI: 使用 design 技能（非 develop）
  ├─ 阶段1: 问题空间探索
  │   ├─ 问：文件大小范围？
  │   ├─ 问：并发量？
  │   ├─ 问：存储需求？
  │   └─ 问：预算约束？
  │
  ├─ 阶段2: 方案生成
  │   ├─ 方案A: 直接上传到服务器
  │   │   优点：简单、控制强
  │   │   缺点：带宽占用、扩展性差
  │   │
  │   ├─ 方案B: 预签名URL到云存储
  │   │   优点：扩展性好、成本低
  │   │   缺点：需要云服务、复杂度高
  │   │
  │   ├─ 方案C: 混合方案（小文件直接、大文件云）
  │   │   优点：平衡性好
  │   │   缺点：维护复杂
  │   │
  │   └─ 推荐：方案B（理由：长期扩展性）
  │
  ├─ 阶段3: 决策支持
  │   ├─ 架构图：[客户端] → [预签名API] → [S3]
  │   ├─ 风险：需要学习S3 SDK
  │   └─ 实施路径：先本地开发、后切云存储
  │
  └─ 阶段4: 文档输出
```

## 软件工程理论支撑

### 1. 关注点分离 (Separation of Concerns)

**理论**：不同职责应该分离到不同模块

**应用**：
- **develop**：功能交付
- **diagnose**：问题修复
- **design**：架构决策
- **review**：质量保障
- **boundary-test**：鲁棒性
- **refine**：持续改进

### 2. 单一职责原则 (Single Responsibility Principle)

**理论**：每个模块只有一个变化理由

**问题**：旧系统中 `brainstorming` 既做需求澄清又做方案探索
**解决**：
- **develop**：明确需求 → 实施
- **design**：不确定需求 → 探索

### 3. 最小惊讶原则 (Principle of Least Astonishment)

**理论**：行为应该符合用户预期

**应用**：
- 用户说"开发登录功能" → 触发 **develop**（直观）
- 用户说"不确定用什么方案" → 触发 **design**（直观）
- 用户说"有个bug" → 触发 **diagnose**（直观）

### 4. 防御性编程 (Defensive Programming)

**理论**：代码应该防御意外输入和状态

**应用**：
- **boundary-test** 技能系统化实施防御策略
- 覆盖输入、状态、资源、数据、业务五大边界

### 5. 测试金字塔 (Test Pyramid)

**理论**：单元测试 > 集成测试 > E2E测试

**应用**：
- **TDD**（develop内置）：单元测试为主
- **boundary-test**：边界和集成测试
- **review**：测试有效性审查

### 6. 持续重构 (Continuous Refactoring)

**理论**：小步快跑改进质量

**应用**：
- **refine** 技能在绿色测试后立即改进
- 红绿重构循环的显式第三步

### 7. 根因分析 (Root Cause Analysis - 5 Whys)

**理论**：追问5次找到根本原因

**应用**：
- **diagnose** 阶段1强制根因调查
- 禁止症状修复

### 8. 契约式设计 (Design by Contract)

**理论**：明确前置条件、后置条件、不变量

**应用**：
- **boundary-test** 验证契约边界
- **review** 检查契约完整性

## 附录B：关键决策记录 (ADR)

### ADR-001: 为什么合并 brainstorming 和 writing-plans 到 develop？

**背景**：
- 用户说"开发X功能"时，需求澄清是必经步骤
- brainstorming 和 writing-plans 总是顺序执行
- 两者间的状态传递增加复杂度

**决策**：合并为 develop 的阶段1和阶段2

**理由**：
- 减少技能切换开销
- 用户心智模型简化（"开发"是一个完整概念）
- 状态管理更简单（单一技能内部传递）

**权衡**：
- ❌ 单个技能变大
- ✅ 流程连贯性提升
- ✅ 认知负担降低

### ADR-002: 为什么新增独立的 design 技能？

**背景**：
- 用户有时只想讨论方案，不立即实施
- brainstorming 混合了"需求确认"和"方案探索"
- 不同心智模式需要不同工具

**决策**：新增 design 技能，专注技术方案探索

**理由**：
- 明确"探索模式"和"执行模式"边界
- 支持纯技术讨论（无需产出代码）
- 符合软件工程"分析-设计-实现"分离

**权衡**：
- ✅ 职责更清晰
- ✅ 灵活性提升
- ❌ 技能数量增加1个（但总数仍减少）

### ADR-003: 为什么 TDD 不再是独立技能？

**背景**：
- TDD 是实施阶段的强制规则，非可选流程
- superpowers 已验证 TDD 必要性
- 独立技能导致"是否使用TDD"的错觉

**决策**：TDD 作为 develop 阶段3的内置规则

**理由**：
- TDD 是"如何做"，不是"做什么"
- 强制执行更符合最佳实践
- 减少用户选择负担

**权衡**：
- ✅ 强制质量保障
- ✅ 流程简化
- ❌ 灵活性降低（但这是好事）

### ADR-004: 为什么新增 boundary-test 技能？

**背景**：
- TDD 主要覆盖 happy path 和已知错误
- 生产环境问题常来自边界和极端情况
- 缺少系统化的边界测试方法论

**决策**：新增 boundary-test 技能，覆盖5类边界

**理由**：
- 补充 TDD 的不足（鲁棒性 vs 正确性）
- 安全漏洞预防
- 系统化边界覆盖策略

**权衡**：
- ✅ 代码鲁棒性大幅提升
- ✅ 安全性增强
- ❌ 测试工作量增加（但值得）

### ADR-005: 为什么合并 requesting-code-review 和 receiving-code-review？

**背景**：
- 两个技能本质是审查流程的不同阶段
- 分离导致流程不连贯
- 状态管理复杂

**决策**：合并为 review 技能，涵盖完整审查循环

**理由**：
- 审查是闭环流程（发起→反馈→修复→再审）
- 单一技能管理整个生命周期
- 简化用户理解

**权衡**：
- ✅ 流程完整性
- ✅ 状态管理简化
- ❌ 技能复杂度增加（但合理）

### ADR-006: 为什么保留 verification-before-completion 作为内置规则？

**背景**：
- 验证是完成的必要条件，非独立活动
- 每个技能结束时都需要验证
- 独立技能增加调用复杂度

**决策**：作为所有技能的内置规则（尤其是 diagnose）

**理由**：
- 验证是质量门禁，不是独立任务
- 减少技能数量
- 强制执行更可靠

**权衡**：
- ✅ 质量保障更严格
- ✅ 流程简化
- ❌ 缺少独立调用能力（但不需要）

### ADR-007: 为什么新增 refine 技能？

**背景**：
- TDD 的 REFACTOR 阶段常被忽略或执行不充分
- 代码质量改进缺少明确指导
- YAGNI 原则需要显式检查点

**决策**：新增 refine 技能，显式化重构阶段

**理由**：
- 明确"绿色测试后"的改进流程
- 系统化质量优化（5个维度）
- 防止过度工程（YAGNI检查）

**权衡**：
- ✅ 代码质量持续改进
- ✅ 技术债务减少
- ❌ 开发时间略增（但长期收益）

## 附录D：FAQ

### Q1: 为什么不保留更细粒度的技能选择？

**A**: 细粒度技能增加认知负担，且实践中总是固定组合使用。合并后的技能仍然是阶段式的，可以在内部灵活控制流程。

### Q2: develop 技能会不会太大？

**A**: develop 是4个阶段的流程，每个阶段职责清晰。虽然包含多个步骤，但用户心智模型是统一的"开发"概念，实际使用更简单。

### Q3: 如果我只想做需求澄清，不想立即实施怎么办？

**A**: 使用 design 技能进行纯方案探索，或在 develop 阶段1完成后明确告知AI暂停。

### Q4: boundary-test 会不会增加太多工作量？

**A**: boundary-test 聚焦关键路径和安全敏感部分，非全量覆盖。实践中，边界问题导致的生产事故成本远高于测试成本。

### Q5: refine 和 review 有什么区别？

**A**: 
- **review**: 检查正确性、发现问题（防御性）
- **refine**: 改进质量、优化代码（进攻性）
- **时序**: review 在任务完成时，refine 在绿色测试后

### Q6: 如果我的团队不想用 TDD 怎么办？

**A**: TDD 是 develop 的内置规则，但可以在项目的 `CLAUDE.md` 中覆盖此行为。不推荐移除，实践证明 TDD 是最有效的质量保障手段。

### Q7: 这套系统适合小项目吗？

**A**: 适合。小项目走 develop 流程会更快（需求澄清简单、计划简短），但质量保障（TDD、review）同样重要。

### Q8: 多人协作时如何使用？

**A**: 每个开发者使用自己的 AI agent + 这套技能系统。代码审查通过 review 技能或人工审查。技能系统不替代团队协作工具。

### Q9: 技能会自动触发还是需要手动调用？

**A**: 
- **自动触发**: develop（识别到开发任务）、diagnose（识别到bug）
- **手动调用**: design（不确定时主动选择）、refine（显式改进）
- **内置规则**: review、boundary-test（由其他技能调用）

### Q10: 学习这套系统需要多久？

**A**: 
- **快速上手**: 10分钟（理解6个技能名称）
- **熟练使用**: 2-3个真实项目
- **精通**: 持续使用1-2个月
